日期：2026-10-15。两种阶段一分词器；7种词表容量；broad/specialized两个训练场景。仅评分既有开发集，不读取测试分数选词表，不改变生产checkpoint、原有实验或PPT。

## 受控设置

容量768、1024、1536、2048、3072、4096、8192；数学基础字母表保持不变（broad596、specialized495），所有原子计入总ID数。BoundaryAST固定tree=.25、boundary=.30。1024/2048重新训练的词表与原checkpoint逐ID完全一致。512无法容纳broad共享字母表，因此不混入这次固定字母表实验。

broad：fit30100+辅助512，开发965；specialized：fit8124+辅助512，开发249。开发数据已在历史研究中可见，本轮是探索，不是新来源确认实验。速度是每容量两方法7轮交错公共encode，受当前机器和小开发集计时影响。内存仅报告持久numpy数组的下限，不是进程RSS或未来LM总内存。

## Cross指标的地位

Cross%是部分跨越token数/token总数。逐字节切分与整式单token两种极端，都可能是0：前者每个token被包含，后者包含全部参考跨度。因此它不是完整数学结构保持程度的单调量。原始字节可逆时数学源码仍可完全恢复，分词改变的是组织粒度/模型学习难度，不是自动丢失了源码结构。

保留Cross作同词表/粒度受控诊断；不把它放入本轮词表主选择。即便按KiB或公式数归一化，也不能解决whole-formula退化。Cmd也只检查命令拼写是否有内部切点，不覆盖变量绑定、运算优先级或推理正确性。

## 现有Fit BPB的意义

它是fit-estimated token unigram的测试/开发理想编码长度除以原字节数。可分解成(T/B)×[测试token频率熵+测试频率到fit概率的KL]。因此同时反映压缩和训练/评估频率匹配；存在合理诊断意义。

但它忽略token顺序，受词表大小和平滑影响，不包含字典本身存储成本，也没有验证可解数学任务。当前的Fit unigram BPB与用训练语言模型条件概率计算的LM BPB不同。后者要在统一数据/计算/架构协议下检验，才更接近模型可学习性。本轮计算alpha=.01/.1/.5/1敏感性，未把BPB并入主排名。

## 审查

28组指标、16996条逐式记录通过三轮实际检查：来源/ID隔离与不评分测试；原有词表再现/同词表对照/原串和payload精确重建；全量逐式与论文macro重聚合及原catalog哈希。BPE为确定性训练，没有用重复随机种子冒充不同词表训练证据。

原始metrics.json/metrics.csv、逐式归档、三轮audits.json和checkpoint均在本目录。Pareto记录仅表示压缩、速度和数组内存下限的非支配点，不宣告下游最佳。
